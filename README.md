# TAiKOTYPiNG ランキング送信テストツール

TAiKOTYPiNG のランキング送信をテストするためのPythonスクリプトです。Python標準ライブラリだけで動作し、実行時にサイトから曲一覧と公開RPC設定を取得します。

> **対策後の互換性について（2026-11-02）**：このスクリプトは旧RPC `submit_ranking_score` に直接送信します。TAiKOTYPiNG側のセッション方式の対策SQLを適用した環境では、この送信は拒否される想定です。以下の使い方は現行スクリプトの操作説明であり、対策後の登録成功を保証するものではありません。公開環境への対策SQLの適用・更新アプリの公開状況は未確認です。

## 動作環境

- Python 3.9以降
- インターネット接続

## 使い方

PowerShellでこのフォルダーを開き、次を実行します。

```powershell
python -X utf8 test_submit_score.py
```

ターミナルに曲一覧が表示されます。曲番号を選び、プレイヤー名・スコア・MAX KPSを入力してください。送信内容を確認し、`y` を入力すると送信します。`0` を選ぶと、一覧にあるすべての曲へ同じテスト結果を送信します。最大コンボが1以上の場合、MAX KPSには0より大きい数値を入力してください。

通常は実行ごとに新しい端末IDを使い、新しいテスト記録を作ります。`--reuse-device` を付けるとローカルに保存した端末IDを再利用し、曲ごとの既存自己ベストを更新します。

```powershell
python -X utf8 test_submit_score.py --reuse-device
```

`--dry-run` を付けると、送信せずに送信予定の内容だけを表示します。

曲一覧・譜面・公開RPC設定の取得通信は行います。`--reuse-device` を併用し、保存済み端末IDがない場合は、端末IDのファイルも作成します。

```powershell
python -X utf8 test_submit_score.py --dry-run
```

## 注意

このツールはランキングデータベースへ記録を送信します。一応作るとSRBに告知しましたが、作成が完了したと報告はしていません。

## 今後ランキングを扱う際の注意点

以下は、2026-11-02時点のTAiKOTYPiNG側の実装と対策内容に基づくメモです。

### 登録経路と対策の確認

- 正規アプリは、プレイ開始時に `start_ranked_play` でセッションを作り、完走後に `finish_ranked_play` で結果を送ります。サーバー側で対象曲・受付開始時刻・有効期限を確認します。端末IDや入力値が形式上正しいだけでは、登録できる条件を満たしません。
- セッションの有効期限は開始から12時間です。初回の登録成功後は、端末ID・スコア・判定数・最大コンボ・MAX KPSを固定し、同じ結果での名前変更を許可します。別のプレイや別の成績に使い回さないでください。
- 旧RPCへの直接送信が拒否されることは、対策適用後の期待結果です。公開キーが取得できても書き込み権限があるとは限りません。登録できない原因を調べるために、旧RPCの公開権限やテーブルへの直接書き込み権限を戻さないでください。
- スクリプトの設定取得は公開JavaScriptの特定の形に依存します。サイト更新で設定を取得できなくなる場合もあるため、設定取得の失敗とサーバー側の登録拒否は区別してください。

### 記録の整合性と自己ベスト

- 最大コンボと `PERFECT + GOOD + MISS` の合計は、実際の譜面の入力対象ノーツ数を超えないようにします。サーバーの `ranking_note_limits` に上限が未登録の曲は受け付けません。曲一覧の表示値だけで判断せず、譜面とサーバー設定を照合してください。
- 最大コンボが1以上でMAX KPSが0の記録は、新規登録が拒否され、ランキング一覧でも非表示になります。スコアは0〜1,010,000、MAX KPSは0〜30の範囲ですが、範囲内であることだけで実際のプレイ結果だと証明できるわけではありません。
- このスクリプトは最大コンボとPERFECT数をノーツ数に固定し、GOOD・MISSを0にします。入力したスコア・MAX KPSとの整合性や実際のプレイを検証する機能はありません。
- 自己ベストは曲IDと端末IDの組み合わせで管理されます。同じ端末IDで低いスコアを送っても過去ベストは下がらず、名前だけが変わる場合があります。HTTPの成功だけで判断せず、応答の `score`・`updated`・`is_new_best` を確認してください。
- 対策SQLは既存記録を自動削除・修正しません。既存ベストがノーツ数上限超過や「コンボあり・KPS 0」に該当すると、その行の更新も拒否される場合があります。非表示と削除を混同せず、修正時は対象行とバックアップを確認してください。`rankings` には `__like__:` で始まるいいね用の行もあるため、一括削除に巻き込まないようにします。

### テストと運用

- まず `--dry-run` で送信先・曲・内容を確認します。現行スクリプトの `SITE_URL` は公開サイトを指しているため、実送信のテストでは管理対象の検証環境を指定したことを確認してください。通常実行は毎回新しい端末IDを作り、`0` の選択は全曲への送信になるため、記録を増やす影響にも注意します。
- 検証環境では、通常プレイの登録・Guest登録後の名前変更・自己ベスト維持ができることと、旧RPCへの直接送信・受付前・期限切れ・登録済みセッションの成績変更・ノーツ数超過・コンボありでKPS 0が拒否されることを確認します。失敗時はエラー内容と登録状況を確認してから再試行します。
- SQLファイルの更新だけではSupabaseに反映されません。既存環境のバックアップと定義を確認し、必要な更新を `supabase_security_fix.sql` → `supabase_ranking_note_limits.sql` → `supabase_ranked_sessions.sql` の順に適用し、対応するアプリも公開します。古いSQLを再実行した場合は、最後に最新版のセッション用SQLを再適用し、旧RPCが公開されていないことを確認します。
- 曲や譜面の追加・変更時は、曲一覧・実際のノーツ数・DBのノーツ上限・受付開始までの時間設定を合わせて更新します。ノーツ上限だけ登録した新曲は利用できますが、`ranked_play_song_durations` に時間設定がない曲には待機時間の検証が働きません。
- 公開anon keyや端末IDは本人認証の代わりにはなりません。`service_role` などの秘密鍵をスクリプト・README・公開アプリに記載しないでください。セッション方式は旧方式の直接送信を抑止する対策であり、偽スコアや大量送信を完全に防ぐものではありません。追加対策は、サーバー側でのプレイ内容の検証や通信回数の制限を検討します。
